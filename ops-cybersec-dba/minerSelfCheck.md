## 一句话结论

**发现挖矿进程时,`kill -9` 是最容易的一步,也正因为容易,它常常等于白做。** 真正该做的是按 **先取证 → 断持久化 → 封出口 → 收兵 → 换锁** 五步顺序,把它的来路一条条掐断 —— **顺序反了,你只是在跟它打地鼠。**

## 故事开场:五分钟后的复活

凌晨收到 CPU 告警,某台机器 load 冲到 30。登上去 `top -c` 一看,一个叫 `kworker/2` 的进程吃了 400% CPU —— **名字看着像内核线程**,但完整命令行里挂着的路径在 `/tmp` 下。

`kill -9`,世界清静了。

**五分钟后监控第二次告警:同一个进程名,PID 换了一个,又活了。**

那天晚上作者做了个笨决定 —— 不杀它了,先查它是怎么回来的。

国家互联网应急中心(CNCERT)发布、**安天科技参与样本分析**的《关于"FakeSvc"挖矿组织大规模传播恶意程序的风险提示》:

| 指标 | 值 |
|---|---|
| 感染时间窗 | 2026-06-15 ~ 2026-07-22 |
| **累计感染设备** | **16,054 台** |
| **单日最高上线肉鸡** | **2,511 台** |

**入侵方式与行为链:**

```
SSH 弱口令暴力破解
        ↓
进入服务器 → 载荷伪装成系统进程
        ↓
通过计划任务实现持久化
        ↓
部署定制版门罗币矿机
        ↓
以受害主机为跳板,继续扫描和爆破同网段设备
```

**所以处置挖矿时,大半的力气不该花在杀进程上 —— 你杀的是它派出来的兵,不是它的家。** 只要定时任务、systemd timer、自启动脚本或父进程守护还在,它就会换一个 PID 回来。

## 三、七项自查清单

> **注意**:5 分钟是"过一遍自查项"的时间,不是"完成处置"的时间。
> 多数命令需要 root;**建议用 sudo 或临时提权执行,别为了跑几条命令长期开着 root 直登** —— 排查不该制造新的风险。

### 3.1 看进程血统,不只看 CPU

```bash
top -c
ps -eo pid,ppid,user,%cpu,comm,etime,args --sort=-%cpu | head -20
ls -l /proc/<PID>/exe
```

**判据:**

- 名字像系统进程、可执行文件却落在 `/tmp`、`/dev/shm`、`/var/tmp` 下 → 优先怀疑
- `kinsing`、`sysupdate`、`networkservice`、`systemd-update` 等名字 → 重点核对
- `ls -l /proc/<PID>/exe` 抓真实路径;文件已删除时会显示 `(deleted)` —— **木马清理落地文件的常见痕迹**

**真假 kworker 的硬判据(三条至少露一处破绽):**

| 检查项 | 真的 kworker | 用户态木马 |
|---|---|---|
| `ps -ef` 的 CMD 列 | 带方括号 `[kworker/0:1]` | 无括号 |
| PPID | **2**(kthreadd) | 通常不是 2 |
| `/proc/<PID>/exe` | **读不到可执行文件**(内核线程) | 可读 |

**两个容易误判的点:**

1. **`ps` 里的 `%cpu` 是进程启动至今的平均值,不是此刻的瞬时占用。** 看近期占用用 `top`;`ps` 的 `%cpu` 适合按存活期平均值粗筛,**不宜据此判断实时趋势**。
2. **不是所有矿马都把 CPU 跑满。** 有些会限速到 30%-50%,甚至挑业务低谷运行。**CPU 没跑满,不等于没中招。**

**隐藏进程的判断要克制:**

```bash
ls /proc | grep -E '^[0-9]+$'
```
连续三次对比它与 `ps -e` 的数量。采集时差、容器 PID namespace(容器里看到的进程编号空间)都会造成偏差。**连续多次明显对不上,只能算一条"高度可疑"的弱线索,别一次就下 rootkit 结论。反过来,数量相同也不能排除隐藏进程** —— 攻击者可能只藏起一两个 PID。

### 3.2 定时任务要查全家桶

```bash
crontab -l -u root
ls -la /etc/cron.d/ /etc/cron.hourly/ /etc/cron.daily/ /etc/cron.weekly/ /etc/cron.monthly/
cat /etc/crontab
cat /etc/anacrontab
systemctl list-timers --all
systemctl list-unit-files --type=service --state=enabled
```

**只敲 `crontab -l` 看到 "no crontab for root" 就收工,等于只查了一扇门。**(没有任务时的这句输出是正常提示,不是报错。)

**路径差异:**

| 位置 | RHEL 系 | Debian/Ubuntu |
|---|---|---|
| 用户任务 | `/var/spool/cron/` | `/var/spool/cron/crontabs/` |
| 认证日志 | `/var/log/secure` | `/var/log/auth.log` |
| sshd 服务名 | `sshd` | `ssh` |

`/etc/anacrontab` 也不是 RHEL 专有 —— Debian 系装 anacron 后同样存在。

**特征字符串**(优先人工核对):`curl`/`wget` 下载后交给 shell 执行、`base64` 解码后执行、`/dev/tcp`。

**现在还要查 systemd timer** —— 新一代木马用它持久化,**只盯 crontab 会漏。**

### 3.3 别漏掉"登录就执行"的开关

```bash
ls -l /etc/rc.local /etc/rc.d/rc.local
grep -nE 'curl|wget|base64|nohup|/dev/tcp' /etc/profile /etc/profile.d/* /root/.bashrc /root/.bash_profile
```

- RHEL 系的实体文件是 `/etc/rc.d/rc.local`,`/etc/rc.local` 一般只是符号链接;**而且要带可执行位**才会被 `rc-local.service` 拉起
- **Ubuntu 18.04 之后很多系统根本没有 rc.local** —— 文件不存在**不等于**被清理过
- 这些启动文件被追加一行下载执行命令,效果是"有人登录就跑一次"。**它没有时间间隔,比 cron 更不规律。**

### 3.4 SSH 不只改密码,还要找它留下的钥匙

```bash
stat -c '%U %a' /root/.ssh/authorized_keys
awk -F: '{print $1, $6}' /etc/passwd
sshd -T | grep -E 'permitrootlogin|passwordauthentication|authorizedkeysfile'
last -20
lastb -20
```

**`authorized_keys` 里有不认识的公钥,就是可能留下的后门。** root 的授权文件通常应是 root 所有、权限 600。

**别只看 `/root/.ssh/authorized_keys`:** 先用 `sshd -T` 看 `authorizedkeysfile`,再按 `/etc/passwd` 里的用户家目录逐个检查;`authorized_keys2`、非 `/home` 家目录和自定义路径都别漏。

**`sshd -T` 的三个限制(易踩坑):**

1. 输出的是**全局生效配置**,`Include` 文件也会展开,但**要 root 才能执行**,而且 **OpenSSH 6.8 以下没有这个参数** —— 老系统只能读 `/etc/ssh/sshd_config` 自己排除注释行
2. 配置里有 **`Match` 块**时,不带 `-C` 的结果**不代表任意连接的最终配置**,还要按具体 `user/host/addr` 用 `sshd -T -C ...` 复核
3. **日志路径别记混** —— 只装 journald、没装 rsyslog 的系统,改用 `journalctl -u sshd --since "7 days ago"`,Debian 系换成 `-u ssh`

**`lastb` 依赖 `/var/log/btmp`。文件不存在,只能说明没有这份记录,不能说明没人爆破过。**

### 3.5 看它在跟谁说话

```bash
ss -tunap
cat /etc/resolv.conf
cat /etc/hosts
```

**看陌生外连。** `ss` 里通常显示为 `ESTAB`,netstat 常显示 `ESTABLISHED`。`-p` 才能看到进程信息,所以要 root;`ss` 直接问内核拿连接表,新系统也通常不再预装 netstat。

**矿池常用 stratum 协议**(矿机与矿池之间领任务、交结果的通信协议),常见端口:

```
3333  5555  7777  8888  9999  14444  45700
```

也有走 80/443 伪装的。

> **但端口不等于证据。** 正常业务也可能占用这些端口,**没看到这些端口也不能排除外连**。要确认,还得看目标 IP、域名及威胁情报。

DNS 配置和 hosts 静态条目也一起看,别只盯连接列表。

### 3.6 `/dev/shm` 要看,chattr 也别混着讲

```bash
find /tmp /var/tmp /dev/shm -type f -perm /111 -mtime -7 -ls
lsattr 文件名
```

- 第一条找的是 **7 天内改动过、又带任一执行位**的文件,符合不少木马落地的画像
- `-perm /111` 表示 user/group/other **任意一边**带执行位;**只写 `-perm -u+x` 会漏掉仅 group 或 other 可执行的少见情况**
- `/dev/shm` 是 tmpfs(内存文件系统),内容不持久保存,**重启后不再保留**。隐蔽性来自"重启即失",不是来自文件加锁。**但 tmpfs 可能使用 swap,不能把话说满**
- 文件删不掉时,用 `lsattr` 看属性串里有没有 `i` 标志。有,就是被加了 immutable(不可变位),**需人工确认后再考虑 `chattr -i` 解锁**
- **边界**:`chattr` 的 immutable **只对 ext4、xfs 等本地文件系统有效,tmpfs 不支持** —— 别在 `/dev/shm` 里看到 "Operation not supported" 就以为工具坏了

### 3.7 你看到的 `ps`,还是原来的 `ps` 吗

```bash
awk -F: '$3==0 {print $1}' /etc/passwd
awk -F: '$3==0 {print $1": "$4}' /etc/group
awk -F: '$4==0 && $1!="root" {print $1}' /etc/passwd
awk -F: '$2=="" {print $1}' /etc/shadow
cat /etc/ld.so.preload
```

- **UID 0 就是超级用户,除了 root 还多出一个,就是高危后门**
- **`/etc/group` 的第 3 字段才是 GID,第 4 字段是成员列表;`/etc/passwd` 则是第 3 字段 UID、第 4 字段 GID** —— 字段位置别写反
- **空密码检查只输出用户名,别把整行 shadow 打印出来,那是密码哈希**
- 正常系统通常**没有** `/etc/ld.so.preload`。文件存在且非空,动态链接器会全局预加载其中指定的库;**合法调试或性能工具也可能这么配** —— 如果不是管理员明确配置的,就要按高度可疑处理,**而不是看到文件就直接定性**

**再校验 `ps` 所属的 procps 软件包:**

```bash
# RHEL 系
rpm -Vf /usr/bin/ps
# Debian / Ubuntu
dpkg -V procps
```

**这两条命令成功执行且没有输出,才代表未发现包文件差异** —— 不是命令失效。执行报错、包不存在或权限不足,**都不能算通过**。

`rpm -V` 有输出时,标记从左到右分别是 `S`=大小、`M`=权限或类型、`5`=内容摘要、`D`=设备号、`L`=链接、`U`=属主、`G`=属组、`T`=修改时间、`P`=能力位,**点号代表该项正常**。

**`lsmod` 可以扫一眼陌生内核模块,但话说回来:能藏住的 rootkit,连 `lsmod`、`ps` 的输出都可能改,校验数据库也可能被一起做手脚。到了这个层面,别再迷信"自己查自己"** —— 用干净的 LiveCD 或把盘挂到另一台机器离线查。

## 四、处置顺序:五步,顺序不能反

![处置挖矿:顺序不能反](assets/checkMiner-01.png)

```
❌ 错误顺序:杀进程 → 打地鼠 → 5 分钟后复活

✅ 正确顺序:
   先取证 → 断持久化 → 封出口 → 收兵 → 换锁
```

### 第一步:先取证

把 crontab、`ss` 输出、可疑文件样本和认证日志**留到本机之外**;云主机可以先打快照。备份日志用 `cp -a` 保留时间戳和权限。

> **留在本机,它删得掉。**

### 第二步:断持久化

注释可疑任务;systemd 服务用 `systemctl disable --now` —— **这是取消自启并停止,不是删除单元文件,证据还在。**

**这一步没做完,别急着杀进程。**

### 第三步:封出口

- **云主机**:优先用安全组封矿池 IP/端口,并把机器从内网信任关系里摘出来
- **物理机**:CentOS 7 常用 `firewall-cmd`;**RHEL 8+、Ubuntu 20.04+ 的 iptables 通常已是 nftables 后端,别硬套老教程**

### 第四步:收兵

**不要机械地背"先子后父"或"先父后子"。** 先确认谁负责拉起:

- 父进程确实是守护者时 → **先处理拉起者,再处理子进程**
- 关系不清 → **回第二步继续查持久化**

```bash
ps -o pid,ppid,pgid,sid,user,stat,args -p <PID>
ps -eo pid,ppid,pgid,sid,user,stat,args | awk '$3 == <PGID>'
ps -o pgid= -p $$
```

**整组 STOP 前,必须同时确认三条:**

1. PGID 大于 1
2. 不等于当前 shell 的 PGID
3. 组内没有 sshd、systemd、容器管理进程或任何业务进程

全部满足,才考虑 `kill -STOP -- -` 冻结整组,观察有没有新副本,再统一处理。**误冻结的恢复命令是 `kill -CONT -- -`。**

> **任何一条不满足,就只操作已确认的目标 PID。生产环境,别把排查变成二次事故。**

### 第五步:换锁

删除确认陌生的授权公钥、修改相关账号密码;若本机存放的用户私钥或 SSH 代理凭据可能泄露,还应轮换对应密钥。

> **攻击者若已写入自己控制的授权公钥,仅改密码不会关闭这条登录通道。**

### 最后一句可能不中听的话

**确认被入侵的生产机器,重装通常比清理更省事,也更可靠** —— 你永远不确定它留了几处后门。

**但顺序仍然不能反** —— 先保全日志和样本,再重装,**别把证据一起格式化。**

## 五、一台中招,别只查这一台

CNCERT 通报里明确提到:**受害主机会被当成跳板,继续对所在网段做 SSH 爆破。**

**同网段、同密钥、同堡垒机可达的机器,至少把第 2 项(SSH)和第 4 项(挖矿痕迹)跑一遍。**

爆破来源统计:

```bash
grep "Failed password" /var/log/secure \
  | awk '{for(i=1;i<NF;i++) if($i=="from"){print $(i+1);break}}' \
  | sort | uniq -c | sort -nr | head -20
```

Ubuntu/Debian 换成 `/var/log/auth.log`。

> **别图省事写成 `awk '{print $11}'`。** `Failed password for root from ...` 和 `Failed password for invalid user admin from ...` 的**字段位置不同**,混着统计会得到一半用户名、一半地址。**按 `from` 关键字取下一个字段才稳,而且 IPv4、IPv6 都能处理。**

**失败登录只代表有人尝试,不等于入侵成功** —— 还要结合 `Accepted` 登录成功记录、授权公钥和异常任务一起判断。

## 六、一键检测脚本 `check_miner.sh`(已修复 + 实测)

**设计原则:只检不改。** 不自动终止进程、不删除文件、不解锁免疫位。**脚本负责找线索,处置决定必须由人来做。**

**输出三级结果:`[危]` / `[疑]` / `[OK]`**,尝试兼容 RHEL 系和 Debian 系。缺少部分可选命令时会提示并跳过;**`ps`、`awk`、`grep`、`find` 等核心用户态工具需要可用。**

**7 个检查项:**

| # | 检查项 | 内容 |
|---|---|---|
| 1 | CPU 与进程血统 | 高 CPU 进程、可疑进程名、kworker 血统、进程计数采样 |
| 2 | 定时任务与 systemd 持久化 | cron 全家桶 + `systemctl list-timers` + enabled 服务 |
| 3 | 登录与启动触发器 | `rc.local`、`/etc/profile.d/`、`.bashrc`、`.bash_profile` |
| 4 | SSH 后门与爆破痕迹 | `sshd -T` 配置、authorized_keys 全家桶、失败登录统计 |
| 5 | 外连与解析配置 | `ss -tunap` + 矿池端口、`resolv.conf`、`hosts` |
| 6 | 临时目录与文件属性 | 7 天内改动且带执行位的文件、immutable 标志 |
| 7 | 账号、加载器与命令完整性 | UID 0、root 组成员、空密码账号、`ld.so.preload`、procps 包校验 |

### ⚠️ 原文脚本有 15 处 bug,直接复制会崩

**本文实测:从原文复制的脚本 `bash check_miner.sh` 在第一次运行时就崩 ——**

```
check_miner.sh: line 17: $1: unbound variable
```

原因:**`warn` / `ok` / `danger` 三个输出函数被调用时,两个字符串参数之间漏了空格**,bash 把 `"进程""缺少 ps，跳过本项"` 拼接成了**一个**参数,而函数需要两个 → `set -u` 下触发 `unbound variable` 直接退出。

**这类 bug 有隐蔽性:** 它不在 `bash -n` 的语法检查里(语法合法),只在**运行时**才炸。而且**第一处崩溃点在第 42 行**(检查项 1 的入口),意味着**脚本连第一项都跑不完** —— 后面 6 项全部不会执行。

**已修复的 15 处:**

|---|---|---|---|
| 1 | L8 | `exportLC_ALL=C` | `export LC_ALL=C` |
| 2 | L214 | `[ -n" $home" ]` | `[ -n "$home" ]` |
| 3 | L218 | `case "$token "in` | `case "$token" in` |
| 4 | L42 | `warn "进程""缺少 ps，跳过本项"` | `warn "进程" "缺少 ps，..."` |
| 5 | L48 | `warn "高CPU""以下进程..."` | `warn "高CPU" "以下进程..."` |
| 6 | L51 | `ok "高CPU""未看到..."` | `ok "高CPU" "未看到..."` |
| 7 | L75 | `warn "进程计数采样""三次采样..."` | `warn "进程计数采样" "三次采样..."` |
| 8 | L92 | `warn "计划任务""部分路径读取失败..."` | `warn "计划任务" "部分路径读取失败..."` |
| 9 | L98 | `ok "计划任务""已读路径未发现..."` | `ok "计划任务" "已读路径未发现..."` |

### 实测发现的两个额外问题

**1. `[危] 可疑进程名` 误报** —— macOS 上 Chrome / Quark / MiniMax 的 `networkservice` 类进程命中了挖矿家族关键词表(`net` / `networkservice`)。**在 Linux 上同样会误报**(很多正常服务名含 `net`)。**这条判据的关键词表需要按业务白名单收紧。**

**2. `-perm /111` 在 macOS 上报错** ——

```
find: -perm: /111: illegal mode string
```

BSD `find` 不支持 GNU 风格的 `/111`(要写 `111`)。**脚本是给 Linux 写的,在 macOS 上这一项会失败**(不影响其他项)。**如果要在 macOS 上跑,需改成 `find ... -perm +111` 或用 `-exec test -x` 替代。**

### 使用纪律

**报告可能包含主机名、内网地址、用户名、cron 内容和完整进程参数,命令行里甚至可能有 token 或口令 —— 不要公开粘贴原始报告,分享前先脱敏。**

**脚本不联网、不上传数据,但它只能发现覆盖到的常见痕迹,查不出所有深度隐藏的内核级 rootkit。全部 OK,只表示这些检查项没发现异常,不等于机器一定没被入侵。**

涉及数据泄露、合规上报,或者已经怀疑 rootkit,**别硬扛,找专业应急团队。**

## 七、本文评价(pros / cons)

### 长处

1. **顺序意识是全文最大的价值。** 「杀进程 → 打地鼠 → 5 分钟后复活」这个错误序列,几乎所有人第一次都会犯。文章把正确顺序固定成五个词(取证/断持久化/封出口/收兵/换锁),**可记忆、可复用**。
2. **每一条判据都标了边界。** "CPU 没跑满不等于没中招"、"端口不等于证据"、"数量相同也不能排除隐藏进程"、"immutable 只对 ext4/xfs 有效,tmpfs 不支持"、"失败登录 ≠ 入侵成功" —— **这种"不要过度解读"的提醒,是实战经验而不是文档搬运。**
3. **PGID 冻结的三个前置条件写得非常克制。** 明确要求"任何一条不满足,就只操作已确认的目标 PID",并给出误恢复命令。**在生产环境这是救命的设计。**
4. **"别再迷信自己查自己"这一段是全文的清醒点。** 能藏住的 rootkit 连 `ps` 输出都能改 —— **明确指出自查工具的极限,并指向 LiveCD / 离线挂盘。**
5. **反直觉的细节都写清了:** `ps` 的 `%cpu` 是历史平均值不是瞬时值;`lastb` 依赖 btmp,文件不存在不等于没人爆破;`sshd -T` 不带 `-C` 在有 `Match` 块时不代表最终配置;`awk '{print $11}'` 统计爆破来源会混。

### 短处

1. **⚠️ 附带的 `check_miner.sh` 有 15 处会导致运行时崩溃的 bug(本文已修复并附上修复版)。** 原文只说"公众号后台回复【获取脚本】领取"—— **如果读者领到的是同一份有 bug 的脚本,第一次运行就会崩,而且崩在第 1 项的入口,后面 6 项全跑不到。** 讽刺的是这正好印证了文章自己的主题:**工具本身也要先验证再信任。**
2. **误报率没有处理。** `net` / `networkservice` 这类关键词在正常业务里非常常见,脚本会直接打 `[危]`。**但脚本的输出设计只有三级,没有"白名单"概念** —— 熟练工要靠人工把误报滤掉,等于把负担还给了人。
3. **"5 分钟自查"的期望值偏乐观。** 7 项检查里有 4 项(SSH 配置、authorized_keys、爆破统计、UID/GID/空密码)**需要 root**才能跑全,而不 root 跑出来的结果里"权限不足"会淹没真实信号。**在真实生产机上,这一轮更可能是 10-15 分钟。**
4. **脚本没有覆盖 systemd unit 文件内容审查。** 第 2 项只列了 `list-timers` 和 `list-unit-files`,**但没有检查 unit 文件的 `ExecStart` 内容** —— 而 `systemd` 恰恰是新一代木马的主要持久化方式。**这是覆盖上的一个实质缺口。**
5. **没有覆盖容器场景。** 文中提到了 PID namespace 作为误判来源,但没有讨论**容器逃逸 / 容器内挖矿 / Docker socket 挂载**这类场景 —— 而这在今天的生产环境占比不低。
6. **CNCERT 数据是 2026 年 7 月的,静态引用。** 挖矿组织的特征(进程名、矿池端口、载荷路径)变化很快,**半年后的检出率会明显下降**。更实用的做法是把关键词表做成可更新配置。
