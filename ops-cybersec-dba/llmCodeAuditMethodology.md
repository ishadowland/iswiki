## 📌 Abstract（摘要）

**文章要解决的矛盾**：LLM 代码审计不能只选规则（会退化成传统扫描器、且规则本身成为召回上限），也不能只选自由推理（同一模型同一项目多次运行结果不同，且无法回答"哪些漏洞类型从未被检查"）。作者的答案是**双向搜索 + 漏洞分类体系 + 分层 Skill 组合**：

- **路径一（反向追踪）**：从危险操作（SQL/命令/文件/网络/模板）沿形参实参向上追到路由入口，检查中间是否有有效防御 —— 适合有明确 Sink 的漏洞
- **路径二（正向推演）**：从 HTTP/RPC/消息入口出发，识别身份/租户/角色/资源所有权，推演状态变化 —— 适合**没有固定 Sink** 的业务逻辑漏洞（越权、支付金额被客户端覆盖、令牌可重放、状态可跳过前置步骤）
- **分类体系三重角色**：能力坐标系 / 运行路由 / 评测切片（从 CWE、OWASP、历史漏洞、企业威胁模型梳理出十余大类百余人小类）
- **不写超长 Prompt**：分层组合「公共发现方法 + 大类方法 + 公共验证方法 + 大类验证方法 + 小类差异知识」，由编排层按需组合
- **发现与验证必须分开**：发现求全、验证求真；发现提假设、验证优先找反证

⭐ **本篇最大的发现不在文章本身，而在它与作者自己 7 月方法论的一处冲突**：作者在 `LLM代码审计方法论-V2`（2026-07）中**明确"反驳"过本文的核心主张之一** —— *"发现 Agent 和反证 Agent 分离即可减少偏差"*，V2 的判断是"角色分离可以改善流程纪律，却不能自动制造认知独立性"。本文（11-20）主张的"发现 Skill 与验证 Skill 必须分开"，正是 V2 反驳过的那条。**同时 V2 又与本文在"验证必须找反证"上完全一致** —— 这不是自相矛盾，而是**同一作者在四个月里对同一问题的两次不同回答**，值得单独记。

⚠️ **一手源的可用性边界（实测）**：仓库 ★17、**只有 3 个 commit（7-19、7-20）**，README 声称的 `schemas/security-claim.schema.json` **整个目录不存在**（README 15 条相对链接里 **3 条失效**）。**文章描述的"系统"没有公开实现**，能核的只有方法论文本。

## 一、为什么"扫描危险函数"不等于"寻找漏洞"

传统静态分析从危险操作开始：SQL 执行、命令执行、文件读写、模板渲染、反序列化、外部网络请求。作者肯定它的价值（明确、快、可复现、能指出"哪里值得继续调查"），但指出它是**候选锚点，不是漏洞**。

⭐ 以 SQL 执行为例，漏洞成立还取决于五个条件：

1. 参数是否来自外部输入
2. 输入怎样跨函数和跨文件传播
3. 中间是否进行了类型约束、白名单或参数化
4. 当前代码是否可以由真实入口触发
5. 危险操作是否在当前运行配置下生效

> *"如果缺少这些条件，扫描器找到的只是一个 Sink，而不是 SQL 注入。"*

### ⭐ 更棘手的一类：没有 Sink 的漏洞

作者列的这几个问题**都没有固定的"危险函数"**：

- 用户是否能修改不属于自己的资源？
- 支付金额是否能被客户端字段覆盖？
- 密码重置令牌是否可以重复使用？
- 某个状态是否能跳过必要前置步骤直接到达？
- 权限检查是否只发生在列表接口，却没有发生在详情和修改接口？

> *"它们往往没有一个固定的『危险函数』。漏洞存在于资源所有权、身份、状态和业务动作之间的关系里。"*

## 二、另一种极端：完全交给模型自由探索

作者承认这种方式"在小项目中可能产生惊喜"，但进入复杂仓库后有四个问题：

| # | 问题 | 表现 |
|---|---|---|
| 1 | **注意力具有偶然性** | 模型可能从用户模块开始，也可能先读配置和依赖；**预算有限时，选择顺序就决定最终结果** |
| 2 | **偏好熟悉的漏洞** | 注入、硬编码凭据等对注入类风险可能有效，却**挤压业务逻辑探索** |
| 3 | **无法回答覆盖度** | "哪些漏洞类型从未被检查"是答不出来的 |
| 4 | **规则零命中不能阻止 LLM 运行** | 未知封装、反射、重导出、内部框架会绕过规则 —— 若"规则未命中"= "无需启动 Agent"，**规则本身就成了 LLM 的召回上限** |

⭐ 由此得出第一条关键设计约束：

> **确定性通道和语义通道相互独立**：规则命中提供线索，但不决定 LLM 是否有资格搜索。

### 四条方法论主张（文章 §四）

| # | 主张 | 要点 |
|---|---|---|
| 1 | **首轮语义侦察独立进行** | 首轮只看项目画像、入口和审计维度，**自主提出候选**；确定性危险点**随后**再作为兜底合并 |
| 2 | **规则零命中不阻止 LLM 运行** | 见上 |
| 3 | **规则负责定位，不越权承担复杂语义裁决** | 正则适合找"像密钥的字符串"，但很难仅凭单行判断占位符、环境变量回退和真实凭据；**过早用复杂正则过滤语义，容易在降低噪声的同时删除真漏洞** |
| 4 | **每次推理都站在代码事实之上** | 项目画像、语法树、调用图、污点流、局部源码不是替模型思考，而是**减少它在文件、行号、调用关系上的猜测** |
| 5 | **发现阶段开放，验证阶段怀疑** | 见 §八 |
| 6 | **用多模型扩大视角，不用投票替代证据** | 不同模型偏好不同 → 互补候选；但"多数模型同意，只能说明假设常见，不能证明漏洞成立" |
| 7 | **用评测和反馈把语义经验沉淀回系统** | 新表达、人工反例、评测缺口 → 反向进入入口与危险点规则、项目画像、发现/验证方法、正反样本、模型与工具组合 |

## 三、双向漏洞搜索（文章 §五，全篇核心）

### 路径一：从危险操作向入口反向追踪

```
定位危险操作 → 找传入危险参数的表达式 → 沿形参实参向上追踪
→ 检查调用者和路由入口 → 检查中间是否存在有效防御
```

**优势**：目标明确，适合确定性工具与 LLM 协作：

| 工具 | 负责回答 |
|---|---|
| 正则 + 语法树 | 快速定位候选 |
| 调用图 | 函数如何连接 |
| 污点流 | 参数传播证据 |
| **LLM** | **理解条件分支、防御语义和框架行为** |

### 路径二：从攻击入口向敏感效果正向推演

```
从 HTTP/RPC/消息入口开始 → 理解当前操作读写什么资源
→ 识别身份、租户、角色、资源所有权 → 推演状态变化和跨接口关系
→ 检查关键约束是否在所有路径一致执行
```

> *"它关注的不是『是否调用了某个危险 API』，而是：**攻击者通过这个入口，最终能够让系统发生什么本不应该发生的事情？**"*

### ⭐ 为什么两条路径不能合并跑

> *"如果自由探索一开始就看到完整危险点清单，模型容易被显眼 Sink 锚定，退化成『逐条解释扫描结果』；如果规则零命中就不启动 Agent，规则本身又会成为 LLM 的召回上限。"*

⭐ **所以系统刻意让语义侦察先独立进行，再将确定性候选作为兜底合并** —— 这是本文最容易被误读成"跑两遍"的地方。

## 四、漏洞分类体系的三重角色（文章 §六）

双向搜索回答了"从哪里找"，但没回答"找得是否全面"。一次扫描可能发现 SQL 注入和硬编码密钥，但仍不知道是否检查过：身份认证 / 资源归属 / 供应链与依赖 / 前端执行上下文 / 并发内存拒绝服务 / 业务状态与金额逻辑。

作者从 **CWE、OWASP、历史漏洞、真实项目案例、语言与框架风险、企业自身威胁模型** 梳理出**十余个大类、百余个小类**。

⭐ **分类体系不是"更长的漏洞百科"，它承担三个角色**：

| 角色 | 作用 |
|---|---|
| **能力坐标系** | 说明当前掌握哪些发现方法、哪些验证方法、**哪些类型仍缺少样本** |
| **运行路由** | 发现疑似风险后，为它**选择相应的调查方法、证据要求和防御检查**，而不是把全部安全知识一次塞进 Prompt |
| **评测切片** | 版本升级后能观察改进发生在哪些语言/框架/漏洞类型，**也能发现总分上升是否掩盖了某类能力退化** |

> *"分类体系解决的不是『让模型知道更多名词』，而是把不可观察的模型能力变成可以管理的问题。"*

### ⭐ 为什么不能写成一份超长 Prompt（§七）

作者给出四个失效原因：

1. **目录完整 ≠ 模型真的逐项执行** —— 列表越长，越容易把"看过名称"误认为"完成检查"
2. **大量共性知识被重复** —— 多个注入小类共享输入可控性/传播/拼接/执行语义；多个权限小类共享身份/资源所有权/授权决策
3. **知识会发生漂移** —— 公共防御标准改变后，同一判断散落上百份文档里很难同步更新
4. **上下文越长，执行越不稳定** —— 安全知识本身会和源码竞争上下文

⭐ **解法：分层组合**

```
公共发现方法  +  当前大类发现方法
公共验证方法  +  当前大类验证方法
                 小类差异知识
        ↓（编排层按当前阶段和候选类型按需组合）
      发现候选  →  证实或证伪
```

- 公共方法：所有类型共享的审计纪律
- 大类方法：该风险族的搜索思路和证据模型
- 小类知识：**只补充特有的 Source、Sink、防御、框架差异和分类信息**
- 编排层：根据当前阶段和候选类型按需组合

## 五、发现 Skill 与验证 Skill 为什么必须分开（§八）

| | 发现 Agent | 验证 Agent |
|---|---|---|
| 目标 | **求全** | **求真** |
| 范围 | 扩大搜索范围 | 收缩到具体候选 |
| 对不完整线索 | 接受 | 证据不足时拒绝下结论 |
| 非常规表达 | 尝试 | —— |
| 反证 | —— | **优先寻找** |
| 检查项 | 攻击面、非常规表达、框架封装绕过、哪些弱线索值得送验 | 外部输入、传播路径、危险效果、有效防御、可达入口、**反证与未决条件** |

⭐ **写进同一份 Skill 的后果**（作者判断）：

- 发现阶段过早自我否定，**弱线索尚未入账就被丢弃**
- 验证阶段继续发散，迟迟不对已有候选结案
- **对自己提出的假设产生确认偏见**

### 四类 Skill 拆分

1. **快速审计总控 Skill** —— 组织"自主侦察 → 候选验证 → 缺口复查"三个阶段，强调**在受控成本内**尽可能找到高价值风险
2. **发现类 Skill** —— 盲态发现与覆盖复查；**只负责提出候选，不负责把候选包装成最终漏洞**
3. **验证类 Skill** —— 专项调查，围绕给定候选检查六项
4. **独立复核方法** —— ⭐ *"审计后的研判 Agent **不直接继承发现 Agent 的自信**，而是重新读取代码，结合业务威胁标准判断风险是否真实成立。"*

## 六、已知类型会不会限制未知漏洞发现（§九）

作者承认分类带来锚定风险：*"如果 Agent 只能在既有目录中选择，它可能把无法归类的新风险强行塞入熟悉类型，或者直接忽略。"*

⭐ **保留的开放通道**：

- 语义侦察**不以规则命中为前置条件**
- 业务逻辑风险**单独探索**，不要求固定危险函数
- 无法立即归类但有代码证据的异常可以继续调查
- 深度模式允许对旁路线索做**有界补查**
- 新型表达经验证后，**再反向补充分类、规则和 Skill**

⭐ **闭环**：

```
既有分类与规则 → 系统搜索 → 发现未知表达 → 独立验证 → 沉淀新方法与样本 →（回到分类）
```

> *"分类的作用不是限制模型只能发现已知漏洞，而是让新发现最终可以被理解、复现和回归。"*

## 七、文章结尾的预告（§十）

作者列出体系已能回答的四个问题（去哪里找 / 已知能力是否触达 / 未知表达如何进入调查 / 为什么不同任务需要不同搜索深度），然后点出下一个更尖锐的问题：

> *"模型说『这里有漏洞』，我们凭什么相信？危险函数可能不可达，调用链可能没有传递攻击者输入，框架可能已经做了防御，模型也可能引用不存在的文件。下一篇文章将讨论整套体系的最后一层：如何把自然语言判断变成能够被代码证据验证、也能够被反证推翻的安全结论。"*

### 8.3 ⭐⭐ 核心发现：V2 明确"反驳"过本文的核心主张之一

`LLM代码审计方法论-V2-反思与重构.md`（2026-07，667 行）的 **§2.5** 标题就是：

> **「反驳：『发现 Agent 和反证 Agent 分离即可减少偏差』」**

原文判断：

> *"**角色分离可以改善流程纪律，却不能自动制造认知独立性。** 如果两个 Agent 使用同一模型、相似提示、相同上下文和相同错误工具，它们的错误高度相关。多角色讨论和多数票不会自动产生独立证据，有时只会把错误说得更流畅。"*

V2 给出的替代方案（**比"分开两个 Agent"严格得多**）：

- 用编译器、查询、测试或运行时观测**验证模型主张**
- ⭐ **让验证阶段看不到发现阶段的严重度和说服性叙述**
- 单独检索 guard、sanitizer、权限检查和不可达条件
- 对关键样本做**盲化人工复核**
- 把"不确定"和"证据不足"作为**正常输出**

⭐ **对照结论**：

| | V2（2026-07） | 本文（2026-11） |
|---|---|---|
| 发现/验证分离 | **反驳**："不能自动制造认知独立性" | **主张**："必须分开"（§八） |
| 目标函数 | *"不是让 AI 尽可能多报漏洞"* | *"如何让 LLM 尽可能找全漏洞"* |
| 验证阶段的独立性来源 | 要求**不同机制**（编译/测试/运行时/盲化人工） | 要求**角色不同**（发现 vs 验证）+ 优先找反证 |
| 未知风险的处理 | 诚实报告没覆盖的部分 | 分类体系 + 开放通道 + 沉淀循环 |

⚠️ **这不是简单的"作者自相矛盾"** —— 更准确的说法是：**本文实现的是 V2 反驳掉的那条路线**（角色分离），而 V2 当时担心的问题（认知不独立）**在本文里没有被正面回应**。

⭐ **但本文并非完全背离 V2** —— 它有一处恰好命中 V2 的要求：**§八「独立复核方法」**说研判 Agent *"不直接继承发现 Agent 的自信"*，以及 §四主张 6 *"用多模型扩大视角，而不是用投票替代证据"*。**这两条方向与 V2 §2.5 给出的补救措施一致**，只是实现层次不同（V2 要求"不同机制"，本文给的是"不同角色 + 不同模型"）。

### 8.4 ⭐ 一手源提供了文章完全没有的四个硬框架

文章完全没提，但 V2 里有：

#### ① 证据阶梯 E0–E5（V2 §4.3）

| 等级 | 含义 | 可做的决定 |
|---|---|---|
| E0 | 只有模型模式匹配或安全直觉 | 仅保留研究假设 |
| E1 | 有准确文件/行/API 与攻击前置条件 | 进入人工初筛 |
| E2 | 调用、控制或数据路径由工具/人工确认 | 可作为有根据候选 |
| E3 | 已检查 guard、sanitizer、配置和反证 | 可进入高优先级验证 |
| E4 | 查询、差分测试、单元/集成测试或形式化条件支持 | 可进入修复流程 |
| E5 | 在代表性环境复现，或获得同等强度的证明 | 可确认技术漏洞 |

⭐ **关键原则**（文章没讲）：**证据等级与业务严重度正交** —— *"一个潜在影响很大的 E1 候选仍是低证据；一个 E5 的低影响漏洞也不应被夸大。"*

#### ② 事实平面 / 推理平面 / 决策平面 三平面架构（V2 §4.4）

```
代码/构建/配置/文档/历史
  → 事实平面（解析、索引、SAST、依赖、运行观测）
  → 上下文编译器（按安全声明生成最小充分证据包）
  → 推理平面（LLM 提出假设、解释路径、寻找反证、生成验证方案）
  → 验证平面（查询、测试、PoC、fuzz、人工核验）
  → 证据账本
  → 决策平面（优先级、阻断、修复、抑制）
  → 评测与运营反馈 → 回到事实平面
```

⭐ **三条硬约束**：
- 事实平面也必须**报告置信边界**
- **推理平面没有直接生产权限**
- **决策平面由显式政策控制，不能由模型自由决定**

#### ③ 评测样本量的实际计算（V2 §5.6）

> *"若观测 precision 约为 80%，希望 95% 置信区间半宽约为 5%，在简单独立近似下需要约 **246 条**经过裁决的系统告警；仓库内样本相关时还需要更多，并应采用按仓库聚类的区间估计。"*

⭐ **作者的判词**：*"20–50 个修复对只能发现流程错误，不能支持『生产可用』或『误报降低多少』的宣传。"*

#### ④ 开放世界 recall 必须诚实命名（V2 §5.7）

不能宣称全局 recall，要分别报告：对历史已知漏洞的 recall / 对人工种植或变异漏洞的 recall / 对专家限定范围审计发现的 recall / shadow 期内对后来确认漏洞的前瞻命中 / 与多个独立检测渠道的新增交集和独有发现。

> *"『未发现』只表示在已报告覆盖、预算和工具条件下没有得到达到门槛的声明。"*

#### ⑤ 三道上线关口（V2 §5.8）

1. **离线关口** —— 隐藏集、困难负例、消融、稳定性和安全边界通过
2. **Shadow 关口** —— 不阻断真实开发；盲化比较人工时间和有效发现
3. **受控决策关口** —— 只对证据门槛明确、历史表现稳定、可快速回滚的少数类型启用自动动作

⭐ **作者对自动阻断的判词**：*"自动阻断不应只看模型历史 precision。它还需要确定性、影响范围、失败模式、业务容忍度、回滚能力和申诉机制。"*

### 8.5 ⭐ 文章与一手源**一致**的三处（交叉印证）

| 文章主张 | 一手源对应 |
|---|---|
| §八「验证 Agent 优先寻找反证，证据不足时拒绝下结论」 | `skills-llm-code-audit.md` §3 状态机明确含 `SeekCounterEvidence → Rejected: 反证成立` 分支 |
| §八「发现 Skill 与验证 Skill 分开」 | 同文件 §2.2 关键要求第 2 条：*"将『发现候选』和『确认漏洞』拆成不同阶段"* |
| §七「不要按 OWASP/CWE 清单逐项问模型」 | 同文件 §3 结语：*"清单驱动适合覆盖提醒，但会产生大量没有路径证据的表面问题。这比『按 OWASP/CWE 清单逐项问模型』更接近真实审计。"* |

⭐ 结论：**文章的主张不是凭空来的**，7 月的一手源已经给出状态机级实现思路。

### 8.6 ⚠️ 一手源 README 的证据分级体系（文章完全没提，但很该被知道）

`purpleroc/llm_code_audit` 的 README 定义了四级证据强度：

| 级别 | 定义 |
|---|---|
| **A：强证据** | 同行评审或公开论文；数据、代码/评测协议基本可得；有基线和明确指标 |
| **B：中等证据** | 技术报告、公开仓库或工业实验；方法和结果可检查，但样本、复现或同行评审不完整 |
| **C：经验性证据** | 技术博客、公众号、演讲或产品材料；可提供工程经验，但**不能单独支持效果结论** |
| **D：线索** | 新闻、聚合转载、无实验宣传；仅作为待核验线索 |

⚠️ **按作者自己的标准，本文属于 C 级**（公众号经验性材料）。⭐ **这恰恰是本次核查该做的事** —— 找到 A/B 级的一手源（仓库方法论）来对照，而不是照单全收。

### 8.7 一手源的**范围说明**（作者自己划的边界）

> *"本调研把『代码审计』限定为发现、定位、解释、验证和修复源代码安全缺陷。安全代码生成、漏洞修复和智能合约审计仅在其方法或评测可迁移到代码审计平台时纳入。**LLM 应用自身的提示注入、越狱等不属于主范围**。"*

### 9.2 普适性缺口（⚠️ 这类最容易漏、后果最重）

| # | 原文结论 | 适用边界与分叉条件 |
|---|---|---|
| 1 | "发现 Skill 与验证 Skill 必须分开" | ⭐ **只在"两个角色共享同一模型/提示/上下文"时成立**。作者自己 7 月的 V2 §2.5 明确指出：角色分离**不能自动制造认知独立性**，真正反证应来自**不同机制**（编译器/测试/运行时观测/盲化人工）。⚠️ **若验证 Agent 用同一模型 + 同一上下文 + 同一错误工具，错误高度相关**，此时"分开"只是流程纪律，不构成独立验证 |
| 2 | "规则负责定位，不越权承担复杂语义裁决" | 成立，但作者自己的 V2 §2.6 补充：*"Skills/MCP 是工作流和工具适配层，不是漏洞发现能力，也不应该成为平台护城河的主要叙事。"* 分叉条件：**若规则本身是唯一信号源**（如无调用图/污点流可用），则"只定位不裁决"会把大量真漏洞留给 LLM —— 此时召回上限仍是规则 |
| 3 | "百余个小类的分类体系" | ⚠️ **分类完整 ≠ 模型真的逐项执行**（作者自己 §七 问题一）。分叉条件：**在长上下文 + 复杂仓库下，目录越长越容易被"跳过"**；V2 §5.7 补充"开放世界 recall 必须诚实命名" —— 分类只能支撑"对已知类型的覆盖"，不能支撑全局 recall |
| 4 | "多模型扩大视角" | ⚠️ 作者 V2 §2.5 更狠：*"多角色讨论和多数票不会自动产生独立证据，有时只会把错误说得更流畅。"* 分叉条件：**多模型 ≠ 独立证据**，除非配合"验证阶段看不到发现阶段的叙述"这类机制 |
| 5 | 全文隐含"让 LLM 尽可能找全漏洞" | ⚠️ **与作者自己 V2 的北极星冲突**。V2 §0 明确：*"新版方法论的核心目标不是『让 AI 尽可能多报漏洞』"*，而是一个净安全收益决策函数（已验证发现的风险降低 − 误报审查成本 − 漏报阻断成本 − 平台运营成本 − 执行不可信代码等自身风险）。**以"找全"为目标会系统性地把 E0/E1 候选也计入成绩** |

## 十、🎯 跟我们的关系

我们做 AI coding agent 工具链 + 工业控制/电力系统上位机，这篇文章有 **五处直接可搬**，其中第 1、2 条与我们最近写的笔记形成闭环。

### 1. ⭐⭐⭐ "每次纠正 agent 都变成一个确定性检查" —— 这篇给了它缺失的另一半

我们在 [all-code-is-slop-except-mine](../ai-vibecoding-agents/all-code-is-slop-except-mine.md)（Lauren Tan）里记的那条原则是**"把纠正下沉成代码"**；本文给的另一半是**"如何决定要下沉什么"**：

⭐ **双向搜索 = 我们验收流程的骨架**：
- **反向追踪**（危险操作 → 入口）= 我们的**静态检查 + 单元测试 + 类型系统**
- **正向推演**（入口 → 业务效果）= ⭐ **我们的缺口**

具体到我们的上位机项目：**"PLC 通讯重连后状态是否可能错乱"、"告警确认是否只做了 UI 禁用而没做服务端校验"、"同一设备 ID 在两个网关下是否会被双写"** —— 这些**没有一个固定 Sink**，正是本文路径二说的那类。这解释了为什么 [cicdVideoReview](../ai-vibecoding-agents/cicdVideoReview.md) 里 Gary 讲的"CI 三关卡全绿不代表现场能跑"是真实风险。

### 2. ⭐⭐⭐ V2 的证据阶梯 E0–E5 —— 我们的验收报告该有的分级

我们现在的验收结论基本是**二元的**（通过/不通过）。⭐ **E0–E5 给了我们一个可落地的分级**，而且它带一条我们一定会犯错的规则：

> **证据等级与业务严重度正交** —— 一个潜在影响很大的 E1 候选仍是低证据；一个 E5 的低影响漏洞也不应被夸大。

⚠️ 我们最容易犯的错正是**把"影响大"当成"证据强"**（比如"这个改动影响告警推送，所以一定重要"）。**证据强度和业务影响必须分两列记。**

### 3. ⭐⭐ 三平面架构 → 我们的 agent 该有的权限边界

V2 §4.4 的三条硬约束，**每一条都直接对应我们的 agent 架构**：

| V2 约束 | 我们的对应 |
|---|---|
| 事实平面必须报告**置信边界** | 我们的工具调用结果要带"我确定/不确定"，不能只回"成功" |
| **推理平面没有直接生产权限** | ⭐ agent 可以提 PR，**不能自己 merge**（正好呼应 Lauren 的"auto-merge 的前提是 codebase 好到 PR 默认就好"） |
| **决策平面由显式政策控制，不能由模型自由决定** | ⭐ 我们的"要不要阻断/回滚"必须是规则，不是 LLM 判断 |

### 4. ⭐⭐ 验证样本量的实际数字：246 条

我们做评测时"抽 20-30 个样本看看" —— V2 §5.6 给了算法：**precision 80%、95% 置信区间半宽 5% → 需要约 246 条经裁决的告警**。

⭐ **这条直接约束我们的验收投入**：20-50 条**只能发现流程错误**（比如我们的报告格式错、断言写错），**不足以支撑"误报降低了多少"的任何宣传**。做 ROI 论证前先算这个数。

### 5. ⭐ 净安全收益决策函数（V2 §0）

⭐ 它的北极星指标不是"发现漏洞数"，而是：

```
净安全收益 = 已验证发现带来的预期风险降低
            − 误报造成的审查与打断成本
            − 漏报和错误阻断成本
            − 计算与平台运营成本
            − 执行不可信代码、泄露源码等平台自身风险
```

⚠️ **最后一项对我们尤其重要** —— 我们跑的是**工业上位机**，让 agent 执行不可信代码、泄露源码的自身风险，不能只算"多发现了几个漏洞"。

## 十一、实战建议

**若要给我们的 AI 审计/验收流程引入这套方法论，按这个顺序：**

1. ⭐ **先定"唯一首要决策场景"**（V2 阶段 A：1–2 周）—— 不是"审计整个项目"，而是"对既有高风险告警做分诊 + 补证据"。**这个收敛建议来自作者自己的实施蓝图，比本文更具体。**
2. **给验收结论加证据等级列**（E0–E5），**并与业务严重度分列**
3. **建"正向推演"通道** —— 从入口/角色/状态出发，不依赖危险函数清单（这是我们最缺的）
4. **让验证阶段看不到发现阶段的叙述** —— 独立复核 Agent 重新读代码，不继承结论
5. ⭐ **验证要靠不同机制，不只靠不同角色** —— 编译/测试/运行时观测/盲化人工，**别用两个同模型 Agent 互证**
6. **诚实命名覆盖度** —— 只报"对已知类型的覆盖"，不报全局 recall
7. ⭐ **算样本量再谈效果**（precision 80% / 半宽 5% → ~246 条）

**明确不建议做的：**
- ❌ 不要把百余个漏洞小类写成一份超长 Prompt（作者自己论证了四个失效原因）
- ❌ 不要用"规则零命中"来决定是否启动 Agent（规则会成为召回上限）
- ❌ 不要用多模型投票替代证据（作者 V2：只会把错误说得更流畅）

## 十二、风险点

- ⚠️ **文章描述的系统未开源** —— 实现无法核验，只能核方法论
- ⚠️ **仓库是资料库不是代码**（★17、无 License、3 个 commit、4 个月未更新）—— 一手源的"当前性"有限，它反映的是 **2026-07 的思考**，不是 11-20 系统的现状
